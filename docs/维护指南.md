# PdfCraft 简体中文版 —— 维护指南

> 面向接手维护本仓库的人 / agent。目标：**在没有历史对话上下文的情况下，也能独立应对上游更新、
> 复现和修复同类问题。**
>
> 最后核对：2026-10-15（上游 v0.8.0 / photocraft v0.9.0 时期）

---

## 0. 一句话背景

用户（非程序员）需要开源 PDF 编辑器 PdfCraft 的**简体中文 Windows 安装包**，并且要修复上游至今
不支持的「新增中文文字显示成问号」缺陷。上游把界面译文用 `include_str!()` 编译进二进制，
所以界面是不是中文只取决于编译的是哪个 commit —— 因此本仓库**不含任何上游源码**，
只在 GitHub Actions 上拉上游源码 + 套用 `overrides/` 里的定制再编译。

两个上游项目均为 MIT OR Apache-2.0 双许可（作者 storytold / ArtCraft）。

| 上游 | 定位 | 本仓库 |
|---|---|---|
| `storytold/pdfcraft` | PDF 编辑器（Rust + egui） | 两个构建仓库之一 |
| `storytold/craft-fonts` | 中日韩字形 | 作为构建依赖拉取 |
| `awpde/photocraft-zh` | PhotoCraft（姐妹项目）的构建仓库 | 见该仓库自己的 `docs/维护指南.md` |

## 1. 双版本策略

| 版本 | workflow | 用途 |
|---|---|---|
| `zh-cjk` | `zh-cjk-windows-build.yml` | **用户实际在用**（认 Latest 徽标）。多一步「应用 `overrides/cjk.patch`」，让新增中文文字能正常显示 |
| `zh-hans` | `zh-hans-windows-build.yml` | 纯中文化（界面 + 字体 + 图标 + 安装界面），**不动源码**，新增中文文字仍是问号 |

两者并存是用户明确要求，不要擅自合并或删除。

触发方式：

| 版本 | 定时 | 手动 |
|---|---|---|
| `zh-hans`（纯中文化） | ✅ `schedule: '0 22 * * *'`（UTC 22:00 = 北京次日 06:00）→ 解析上游**最新 Release tag** | ✅ `workflow_dispatch` |
| `zh-cjk`（含中文输入修复） | ❌ **已停用，见 §1.5** | ✅ `workflow_dispatch`（`upstream_ref` 默认 `v0.9.0`） |

## 1.5 ★ zh-cjk 定时构建：已停用与恢复方法

**状态：2026-10-19 起，`zh-cjk` 只有手动触发。用户日常用的是 `zh-hans`。**

### 为什么停

1. **用户用不到这个功能。** 他日常对 PDF 做的是**合并、删页、涂黑**——这三样纯中文化版都有。
   补丁唯一解决的是「**新增中文文字**」（上游至今不支持，见 issue #455）。
2. **它是整个仓库唯一需要人工维护的环节。** `cjk.patch` 只对一个上游版本有效，
   上游**平均 1.8 天发一版**（2026-10-02 的 v0.1.0 → 10-18 的 v0.9.0，10 个版本），
   每发一版都要重新生成并推送一次补丁，然后手动触发、验证。
3. **上游不会接手这份补丁。** 他们的 `AGENTS.md` §1.1 **明令禁止捆绑中文 CJK 字体**
   （点名 Adobe CJK / Noto CJK / Source Han），与本补丁「用日文字体画中文」的思路冲突。
   相关 issue #455 自 2026-10-09 起 open，贡献者 10-10 就备好了可合并分支，至今未合。
   → 这意味着维护成本是**长期的**，不会随着上游成熟而消失。

结论：为一个用不到的功能，每 1.8 天做一次人工维护，不划算。
停掉之后用户不再收到构建失败邮件，也不需要为这个项目做任何事；
`zh-hans` 继续每日自动跟版，**零维护**。

### 怎么恢复（约 5 分钟）

> ⚠️ **第 1 步不能跳。** 补丁只对准一个上游版本（铁律 2），
> 直接把 `schedule` 打开，第一次跑**必然失败**——用户会收到失败邮件。

```bash
# 1) 查上游最新 tag，并确认现有补丁是否还适用
gh release list --repo storytold/pdfcraft --limit 1
python tools/regen-cjk-patch.py --check-ref <最新tag>      # 若这里报「应用失败」，说明必须重新生成

# 2) 重新生成并推送补丁（脚本自带全部校验）
python tools/regen-cjk-patch.py <最新tag> --push
python tools/regen-cjk-patch.py --check-ref <最新tag>      # 再确认一次

# 3) 手动触发一次，端到端验证
gh workflow run zh-cjk-windows-build.yml --repo awpde/pdfcraft-zh -f upstream_ref=<最新tag>
#    等它跑完，然后**必须回读日志**（铁律 3.1）：
python tools/fetchlog.py awpde/pdfcraft-zh <run_id> "已应用 CJK|已确认 added.rs|已替换|补充译文：|ok MSI"

# 4) 验证通过后，打开定时
#    编辑 .github/workflows/zh-cjk-windows-build.yml，把文件顶部那段注释掉的
#      schedule:
#        - cron: '0 22 * * *'
#    取消注释即可，其余部分不用动。

# 5) 同步更新本文档 §1.5 的状态描述，以及 AGENTS.md §1 / §1.1
```

### 如果用户只是想「临时要一个能加中文的包」

那**不用恢复定时**，直接手动构建当前可用的版本就行：

```bash
gh workflow run zh-cjk-windows-build.yml --repo awpde/pdfcraft-zh \
  -f upstream_ref=v0.9.0        # = 补丁当前对准的版本
```

### 停用期间的状态记录

| | |
|---|---|
| 补丁当前对准 | **pdfcraft v0.9.0** |
| 可用的 zh-cjk release | 见 Releases 页里标题含「含中文输入修复」的那些 |
| 用户日常使用 | `zh-hans`（Latest，v0.9.0 及之后每天自动更新） |

> **上游更新期间 zh-hans 偶尔也会失败** —— 那是 §6.2 的安装界面校验问题，与本次停用无关，
> 按正常流程修即可（不需要动补丁）。

```
│   ├── minipatch.py                 # 纯 Python 的 unified diff 生成 / 应用

│   ├── regen-cjk-patch.py           # ← 重新生成 cjk.patch 的主脚本

    └── zh-hans-windows-build.yml
```

### `overrides/` 各文件的作用

1. **`cjk.patch`** —— 给 `crates/edit/src/added.rs` 打补丁，用 craft-fonts 里的日文字体
   （Shippori Mincho）通过 **Type 3 字体回退**画 CJK 字符。**当前对准上游 v0.9.0**。
2. **`installer-ui.wxs`** —— 基于上游最新版 + 我们的「自选安装位置」自定义。
   **上游新增控件必须保留**，上游 `packaging/windows/test-msi.ps1` 会逐项校验。
3. **`zh-hans-补充译文.tsv`** —— 42 条上游缺失的中文翻译。workflow 在编译前**条件追加**：
   只补上游确实缺的条目（整行精确比对 context + source），上游将来自己补了不会产生重复键。
4. **`fonts/harmonyos-sans-sc/`** —— 替换界面字体（上游默认字体不含完整简体中文字形）。
   鸿蒙 Sans SC 允许嵌入/捆绑再分发，但要求显著声明 + 不得修改 + 保留协议，
   因此 `OFL.txt` **必须随包分发**（workflow 会校验便携版里有它）。
5. **`icons/`** —— 见 §5 的「三处图标」。

## 3. 构建流程（以 zh-cjk 为例）

```
resolve job（解析目标：定时取上游最新 Release tag / 手动取输入的 ref）
keepalive job（距上次提交超 50 天补空提交，防止定时任务被 GitHub 停用）
build job:
  1-3   拉取上游源码 / 本仓库 / craft-fonts
  4     应用「新增中文文字」修复补丁      ← zh-cjk 独有；失败 = 中止构建（设计如此）
  5-7   应用鸿蒙界面字体 → 校验字体清单 → 精简字体目录
  8     应用「自选安装位置」界面
  9     替换软件主图标 + PDF 文档图标 + 窗口图标 PNG（三处全换）
  10-11 安装 Rust / 缓存 → 校验中文词条（含 42 条条件追加）
  12-13 安装 WiX 5 → 编译打包（官方 package.ps1 → MSI + 便携版 zip）
  14    校验 MSI 带上了自选安装位置界面
  15    校验 exe 内嵌入了指定中文字体
  16    生成许可证与改动声明（MIT / Apache / NOTICE / 非官方声明 四件套）
  17    上传产物 + 创建或更新 Release
```

workflow 关键环境变量（改字体只需改 `ZH_FONT_*` 三行）：

| 变量 | 当前值 |
|---|---|
| `UPSTREAM` | `storytold/pdfcraft` |
| `ZH_CATALOG` | `crates/ui-egui/src/i18n/zh-hans.tsv` |
| `CRAFT_FONTS_REF` | `8dcdacd5153e64560d109541a47d806f26f048c0`（必须含 Hans 脚本字体） |
| `ZH_FONT_FAMILY` / `ZH_FONT_DIR` / `ZH_FONT_FILE` | `HarmonyOS Sans SC` / `harmonyos-sans-sc` / `HarmonyOS_Sans_SC_Regular.ttf` |
| `UPSTREAM_UI_SHA256` | `a437c2a8…`（我们合并安装界面时依据的上游指纹；变了会在日志里提醒） |

## 4. 铁律

### 铁律 1 —— 永远不要只看绿对勾，必须回读构建日志

`gh run list` 显示 success **不代表**定制都生效。必须下载 build job 日志，逐条确认下列行
**真实执行**（有时间戳前缀、无缩进；脚本里 `echo` 的回显是缩进的，别混淆）：

| 要找的行 | 含义 |
|---|---|
| `✅ 已应用 CJK 修复补丁` + `已确认 added.rs 含 draw_cjk` | 补丁真正生效 |
| `✅ 已替换软件主图标（狮子 → 自定义）` | exe 资源 1 已换 |
| `✅ 已替换 PDF 文档图标` | exe 资源 2 已换 |
| `✅ 已替换窗口图标 PNG（编译期内嵌的那张）` | 窗口左上角已换 |
| `补充译文：X → Y 行（新增 42 条）` | 翻译补齐生效 |
| `ok MSI` | MSI 自检通过 |
| `✅ 简体中文译文已…编入 exe` | exe 确实含中文 |

回读日志（不依赖 git，Windows 上稳定）：

```bash
python tools/fetchlog.py awpde/pdfcraft-zh <run_id> "已应用 CJK|已替换|补充译文：|ok MSI"
```

> `fetchlog.py` 匹配不到任何行时会明确报错并提示 —— 这正是它要抓的情况：
> **定制根本没执行**，哪怕 job 是绿的。

### 铁律 2 —— 补丁必须对准上游 **Release tag**，不是 `main`

定时任务跟的是上游最新 Release tag。补丁只能精确匹配一个版本。
把补丁对准 `main` 会导致**定时任务全挂**，而手动构建（用 `main`）却成功 —— 极易误判。

> 实例：曾把补丁对准 `main`（`added.rs` 1096 行），而 v0.7.1 是 1083 行且 `width()` 签名不同
> → 定时构建全部失败，用户收到 GitHub 失败邮件来催。

**验证补丁是否仍适用**（最快的方式）：

```bash
python tools/regen-cjk-patch.py --check-ref v0.8.0
```

### 铁律 3 —— 上游发新版后，「补丁」和「安装界面」是两处独立的失效点

它们在不同步骤失败、不同时间修复，**不要只修一个就以为好了**。见 §6。

### 铁律 4 —— 仓库根目录的 `.gitattributes` 不能删

```
*.patch -text
*.tsv -text
```

没有它，GitHub Actions 的 Windows runner 会在 checkout 时把文本文件转成 CRLF，
导致 `overrides/cjk.patch` 与上游 LF 源文件行尾不一致 → `git apply` 失败；
译文 tsv 追加时同样会被污染。

## 5. 图标：三处机制

一个 Windows 桌面软件显示图标的位置有三处，**来源各不相同**：

| # | 位置 | 来源 | 替换方式 |
|---|---|---|---|
| 1 | exe 资源 1（任务栏 / 开始菜单 / Alt-Tab / 快捷方式） | `assets/app-icon/pdfcraft.ico`（`build.rs` `set_icon`） | 覆盖 `overrides/icons/pdfcraft.ico` |
| 2 | exe 资源 2（PDF 文件关联图标，installer 用 `pdfcraft.exe,-2` 引用） | `assets/app-icon/pdfcraft-document.ico`（`set_icon_with_id(...,"2")`） | 覆盖 `overrides/icons/pdfcraft-document.ico` |
| 3 | **窗口左上角图标** | `assets/app-icon/hicolor/256x256/apps/ai.storyteller.pdfcraft.png`，`main.rs` 用 **`include_bytes!` 编译期内嵌**再 `viewport.with_icon()` | **必须换这张 PNG，换 ico 对它无效！** |

用户最终确认的方案：

| 位置 | 图标 | 外观 |
|---|---|---|
| 软件主图标 + 窗口图标 | 用户定制的**大红 P** | 白色折角文件 + 大红字母 P + 米色纸面 + 红描边 |
| PDF 文件关联图标 | **方案 A** | 与上游原图标同结构，仅绿色换成红色（白纸 + 红色「PDF」徽章 + 白字） |

> ⚠️ **历史教训**：用户导出的文件名叫 `pdf图标.png`，但内容其实是**软件主图标**。
> 曾按文件名误判，把大红 P 装到了 PDF 文档图标位置。
> **判断图标归属必须看图片内容 + 对话上下文，不能信文件名。**

### 换图标的步骤

1. 拿到新图（透明背景、≥512px 最佳）
2. 处理成目标格式（Pillow 环境见 §9）：
   - **ico**：裁剪透明边 → 正方形画布居中（上下贴边）→
     `img.save('x.ico', format='ICO', sizes=[(16,16),(20,20),(24,24),(32,32),(40,40),(48,48),(64,64),(128,128),(256,256)])`
     > ⚠️ **必须用 `sizes=` 让 Pillow 自动缩放，不能用 `append_images`**（ICO 格式下
     > `append_images` 无效，只会存第一个尺寸）。
   - **窗口图标 PNG**：同样裁剪贴边后 `resize((256,256))` 存 PNG。
3. 推送覆盖 `overrides/icons/` 对应文件（`hicolor-256-app.png` 容易被漏，别忘）
4. 触发构建，按**铁律 1** 回读日志确认三行图标替换都执行

### 图标源文件

源图、设计稿、交互式调图标工具全部保存在仓库的
**[`docs/icons/`](icons/)**（含一份说明文件，讲清每个文件是什么、哪个是真源，以及**踩过的坑**）。

> 用户亲手调的源头图 `软件图标-用户定稿原图.png` 是**唯一真源**，`overrides/icons/` 下的
> `pdfcraft.ico` 和 `hicolor-256-app.png` 都由它生成，ico 无法反推回原图。
> **改图标前先看那份 README，不要按文件名猜归属** —— 这里出过两次事故。

## 6. 上游更新后的处置流程

上游更新非常频繁（2026-10-08 的 v0.4.0 → 10-12 的 v0.7.1 → 10-14 的 v0.8.0，
`added.rs` 从 917 行涨到 1096 行）。下面的故障是**常态，不是异常**。

### 6.1 zh-cjk 挂在「应用补丁」步骤（最常见）

**现象**：`error: patch failed: crates/edit/src/added.rs:NNN` + `patch does not apply`，
构建 **30 秒左右**秒挂。

**根因**：上游更新了 `added.rs`（结构 / 行号 / API 变化），补丁打不上。**补丁必须对准定时任务
要跟的那个 Release tag。**

**修复**（一条命令，脚本自带全部校验）：

```bash
# 0) 先确认现有补丁是否已经失效（最省事的一步）
python tools/regen-cjk-patch.py --check-ref v0.8.0

# 1) 生成 + 自检（不推送，先看输出）
python tools/regen-cjk-patch.py v0.9.0

# 2) 确认无误后推送
python tools/regen-cjk-patch.py v0.9.0 --push

# 3) 手动触发一次 upstream_ref=v0.9.0 的 zh-cjk 构建，精确模拟定时任务路径
gh workflow run zh-cjk-windows-build.yml --repo awpde/pdfcraft-zh -f upstream_ref=v0.9.0
# 4) 按铁律 1 回读日志
python tools/fetchlog.py awpde/pdfcraft-zh <run_id> "已应用 CJK|已确认 added.rs|已替换|补充译文：|ok MSI"
```

> **改脚本之后**，务必跑一次回归测试确认它仍然忠实复现当前补丁
> （它比对「现有补丁」与「脚本 6 处改动」两条独立路径的产物）：
>
> ```bash
> python tools/verify_regen.py v0.8.0
> ```

脚本做的 6 处改动（每处都断言锚点在目标文件里**恰好命中 1 次**）：

| # | 位置 | 改动 | 版本适配要点 |
|---|---|---|---|
| 1 | import 区 | **加一条独立 use 语句**：`use pdfcraft_fonts::{CraftFont, document_japanese_fonts_for_style, japanese_glyph_from};` | **绝不改原有 import 行**。v0.7.1 是多行块（含 `helvetica_width`），v0.8.0+ 是单行含 `Std14`；独立 use 两边都成立 |
| 2 | `first_undrawable` | 在**泰文块之后**、阿拉伯/希伯来之前插入 CJK 判断 | 锚点用泰文块的收尾 `return first_undrawable(&rest);` + `}`。**不要用阿拉伯那句注释当锚点** —— 上游每加一种文字就改它（v0.9.0 从 "Arabic that…" 改成了 "Arabic or Hebrew that…"） |
| 3 | `shaped_arabic` 之后 | 加 `fn is_cjk(c: char) -> bool` | **排除列表由脚本自动探测**（见下方「上游加新文字脚本」），不要手写 |
| 4 | `/// Content and resources for an item` 注释前 | 插入完整 CJK 实现块（223 行），见 `tools/cjk-block.rs.txt` | 块内 `t.family.width(...)` 的参数个数随版本变化，由脚本自动判定 |
| 5 | `draw` 里 shaped 分支之后 | 插入 CJK 分发：`if needs_cjk(&t.text) { draw_cjk(...)?; ... }` | 锚点用 `draw_shaped(doc, t, taken, &mut fonts, &mut out)?;` 调用本身。**收尾的 `}` 要按「调用行缩进 − 4」去找** —— 直接按调用行缩进找会匹配到分支内部更深的括号，插到错误位置（这个 bug 真实发生过） |
| 6 | `own_fonts` | 过滤器加 `\|\| w.starts_with(b"PCCjk")` | 清理 CJK Type 3 字体 |

#### 上游加新文字脚本时，`is_cjk` 必须跟着排除 ★

**这是本补丁最隐蔽的失败模式**，而且不会在生成补丁时报错，只会在**编译/运行时**炸：

> 上游每支持一种新文字（Arabic → Thai → Hebrew），就会多一个 `fn is_xxx(c: char) -> bool`。
> 这些字符**上游自己用 craft-fonts 的字体就能画**。如果 `is_cjk` 没排除它们，
> 我们的分发逻辑就会把它们送进**日文字体**去画 —— 而日文字体没有对应字形，
> 报错形如 `Japanese fallback font has no glyph for U+XXXX`。

希伯来语在 v0.9.0 加入时，正好把泰文当初那个坑又复现了一遍。

**现在的做法**：脚本用 `upstream_script_guards()` 扫描目标文件里所有
`fn is_xxx(c: char) -> bool` 定义，自动生成排除列表；静态检查还会复核
「上游有的每一种，`is_cjk` 里都排除了」。所以**上游以后再加新文字，这里不用改**。

> 若哪天真的报出缺字形而脚本的排除列表又是全的，说明上游用了别的形式声明可绘制脚本
> （不是 `is_xxx(c: char) -> bool`），需要把那个名字补进 `upstream_script_guards()` 的排除集。

**版本系判断诀窍**（脚本会自动做，这里留作人工核对）：

```bash
grep -n "pub fn width" added.rs     # 三参数 (s,size,bold) = old 系；四参数 (+italic) = new 系
```

已验证：v0.7.1 = old 系（1083 行 / 3 参数）；v0.8.0 / v0.9.0 = new 系（1096 / 1151 行 / 4 参数）。

**脚本的保底校验**（任何一项不过就中止，绝不产出坏补丁）：

- 锚点唯一性（6 处）
- 生成后立刻把补丁应用回原始文件，必须**逐字节**等于修改后的文件
- 括号配平
- `width()` 调用参数个数 == 上游签名参数个数（剔除 `self`）
- 上游原有 import 行未被改动
- `is_cjk` 含 `!is_thai(c)`
- 补丁是**纯 LF**（零 CR）

## 7. Windows / PowerShell 踩坑集

这些坑都真实发生过，且**本地往往复现不出来**，只会在 CI 上炸。

### 7.1 pwsh（PowerShell 7）vs 本机 PowerShell 5.1 的排序规则差异 ★

- workflow 里 Windows 步骤的 shell 是 **`pwsh`（.NET Core / ICU）**，
  本机是 **PowerShell 5.1（.NET Framework / NLS）**
- ICU 排序规则**把控制字符视为可忽略** → `"\r".StartsWith("\x01")` 在 pwsh 上是 **True**，
  在 5.1 上是 **False**
- 教训：任何字符串前缀/比较判断一律用 `[StringComparison]::Ordinal`，别用 culture-sensitive 默认重载。
- **「本地过了 CI 挂了」时，第一反应就怀疑这个差异。**

### 7.2 CRLF 污染

- 上游词条文件在注释头之后有**空行**；Windows runner 检出为 CRLF → 空行变成单个 `\r`（0x0D）
  → 被上游 build.rs「非词条行原样保留」打进二进制 → 校验脚本误判成空译文条目
- 修复要点：跳过空行 / CR 行时**仍要把它原样追加到重建文本**，否则后续「逐字节比对源文件」会因少行而失败
- 做字符串锚点匹配前**必须先归一化** `content.replace('\r\n','\n')`，
  否则远端文件（可能 CRLF）锚点命中 0 次，报出「已被他人改动」的误判
- 补丁 / tsv 一律**纯 LF**，靠 `.gitattributes` 保证（铁律 4）

### 7.3 含中文的 `.ps1` 文件必须加 UTF-8 BOM

否则 PowerShell 5.1 按 ANSI 解码 → 语法错误（表现为莫名其妙的「字符串缺少终止符」）。
测试脚本建议直接写纯英文。workflow 里内联的 pwsh 脚本不受影响（pwsh 默认 UTF-8）。

### 7.4 本机没有 git 和 patch

维护用的 Windows 机器**没有安装 git，也没有 GNU patch**。
所有补丁生成 / 应用 / 验证都靠 `tools/minipatch.py`（纯 Python 的 unified diff）。
生成产物是标准 unified diff，在 runner（有 git）上 `git apply` 能正常吃下。

### 7.5 PowerShell 里调用 `gh` 的参数解析

`gh api ... --jq '.[] | ...'` 在 PowerShell 下常被拆成多个参数而报
`accepts 1 arg(s), received 2`。改用 `tools/ghapi.py`（走 curl + Python JSON 解析）。

### 7.6 「所有 API 调用都 404 / 返回空」——先查 hosts，再查 token ★

2026-10-22 踩过。这两个症状长得几乎一样，**很容易误判成 token 失效甚至仓库被删**。

**真凶**：本机装了一个 GitHubHosts 工具（桌面 `GitHubHosts\Update-GitHubHosts.ps1`），
它会改写 `hosts` 文件，把所有 GitHub 域名指向某个 IP。
2026-10-20 那次写入的 IP（`20.27.177.113`）上：

| 域名 | 表现 |
|---|---|
| `github.com` | ✅ 200（网页正常，所以很容易以为网络没问题） |
| `api.github.com` | ❌ **301 跳到非法地址 `github.com/repos/…`，响应体为空** |
| `raw.githubusercontent.com` | ❌ **连接被重置** |

`gh` 收到空响应就报 `404 Not Found`，`gh auth status` 也会说「token 无效」——**都是假的**。

**诊断顺序**：

```bash
# 1) 先看 hosts 里 GitHub 域名被指到哪了
findstr /i github %SystemRoot%\System32\drivers\etc\hosts

# 2) 绕过 hosts 试一下（换一个已知可用的 IP）
curl --resolve api.github.com:443:20.205.243.168 https://api.github.com/repos/storytold/pdfcraft
#    上面这条返回 200 = token 没问题，是 hosts 的锅
```

**处理**：让用户跑 `GitHubHosts\一键恢复默认hosts.bat`，或 `一键更新GitHubHosts.bat`（会重新测速选 IP）。

**已做的加固**：`tools/ghapi.py` 里的 `api()` 在直连拿不到合法 JSON 时，
会自动用 `--resolve` 换一组已知可用的 IP 重试 —— 不依赖 hosts、不需要管理员权限。
所以即使 hosts 又被写坏，工具链仍能工作。

> `raw.githubusercontent.com` 的 IP 段（`185.199.x.x`）在部分网络下全被阻断。
> 读仓库文件请用 API 的 Contents 接口（`tools/ghapi.py` 的 `content()`），
> 不要依赖 raw 域名。

### Release 是否真的更新了 —— 看资产的 `updatedAt`，不是 `publishedAt`

```bash
gh release view <tag> --repo awpde/pdfcraft-zh --json assets \
```
